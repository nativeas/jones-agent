## 前置条件

- 一台可以安装 LaunchAgent 的开发机（不要用 CI）。
- 打包产物或本地 `python -m jones_daemon service install`（见
  `daemon/src/jones_daemon/service.py`）。

## 步骤（分三段）

### 段 1：Cron 独立于 Electron

1. `python -m jones_daemon service install`，确认 `launchctl print` 能看到
   `ai.jones.daemon` 处于 loaded 状态。
2. 打开 Jones，配置一个 1 分钟后触发一次的 Cron（`cron.upsert`，`* * * * *`
   或具体到下一分钟的表达式）。
3. **完全关闭 Electron**（Cmd+Q，不是最小化）。用 `ps aux | grep jones_daemon`
   确认守护进程仍在跑。
4. 等待 Cron 触发时间过去（1-2 分钟）。
5. 重新打开 Electron，检查主会话里是否出现该 Cron 派发的结果消息。

### 段 2：崩溃后 launchd 自动拉起

6. 记下当前 daemon 的 pid（`launchctl print gui/$(id -u)/ai.jones.daemon`
   或 `ps aux`）。
7. `kill -9 <pid>`。
8. 等待 5 秒，检查 daemon 是否已被 launchd 重新拉起（pid 变化、`daemon.ping`
   能通）。

### 段 3：连续拉起失败的显式报错

9. 制造一个会让 daemon 反复启动失败的情况（例如临时把
   `~/.jones/jones.db` 替换成一个无法解析的垃圾文件，或指向一个不存在的
   Python 解释器路径），让 launchd 连续 3 次拉起都失败。
10. 打开 Electron，确认它检测到连续 3 次拉起失败后显式报错（不是无限转圈、
    不是白屏），见 `apps/desktop/src/main/__tests__/daemonLifecycle.test.ts`
    的 `reports unreachable exactly once after exhausting all retries` 这段
    单元覆盖对应的真实观感。
11. 恢复现场（还原 `jones.db`/解释器路径），`service uninstall` 清理
    LaunchAgent。

## 期望

- 段 1：Electron 关闭期间 Cron 照常触发，重开后能看到结果。
- 段 2：崩溃后 5 秒内 launchd 把 daemon 重新拉起。
- 段 3：连续 3 次失败后 UI 有明确、可读的错误提示，不是挂死。
