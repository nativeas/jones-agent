## #36 解除记录

见 `gh issue view 36 -R nativeas/jones-agent` 与 `docs/release.md` §2.2/§2.3
（完整实测记录）。根因：`cryptography==50.0.0`（daemon 精确依赖，被
hermes-agent 自己的 exact pin 挡死、不能降版本）在 PyPI 上没有发布 macOS
x86_64 wheel，必须从 sdist 源码编译（需要 Rust），而这个编译不能在 arm64
主机上交叉完成——本机（arm64）实测复现过链接阶段失败。

**采用方案 (a)**（#36 原文候选之一）：CI 加一个原生 Intel runner 直接出
x86_64 包，不在 arm64 主机上交叉编译。已落地并真实跑通：

- 工作流：`.github/workflows/release-bundle.yml`（`workflow_dispatch` +
  push `v*` tag 触发）。两个矩阵 job，都是原生编译：`x64` 腿用
  `macos-15-intel`（原生 x86_64 标准 runner——Issue #36 原文写的
  `macos-13` 已于 2025-12 被 GitHub 完全退役，实测踩过这个坑，见
  `docs/release.md` §2.3），`arm64` 腿用 `macos-14`（原生 arm64）。
- 真实跑通记录：run
  [`35693372847`](https://github.com/nativeas/jones-agent/actions/runs/35693372847)——
  `x64` 腿日志里能看到 `cryptography==50.0.0` 从 sdist 用 runner 自带的
  Rust 工具链真实编译了 2:47（不是拿到了意外的 wheel、也不是伪装通过），
  两个架构的 `daemon-bundle-<arch>` artifact 都完整（含
  `DEPENDENCY-REPORT.md`、`bin/jones-daemon`、hermes-agent 源码树）。完整
  时间线、bug 修复记录见 `docs/release.md` §2.3。
- **CI 只出到「daemon bundle」这一层**，不是签名好的完整 `.dmg`——
  `scripts/release/build-mac.sh` 后面 electron-builder 打包 + ad-hoc 签名
  那几步没有接入这个工作流（#36 本身只要求证明 x86_64 daemon 产物能被造
  出来）。要拿到 `Jones-<version>-x64.dmg`，需要把 CI 产出的
  `daemon-bundle-x64` artifact 接进 `build-mac.sh` 的后续步骤（本分支未
  做，留给执行下面「前置条件」时手动补，或后续另开 Issue 把完整 `.dmg`
  管线也搬上 CI）。

**为什么真机验收这一步不能被 CI 代替**：CI 的 `macos-15-intel`/`macos-14`
runner 证明的是"这份产物能在原生 x86_64/arm64 上被**构建**出来"，不是"这个
`.app` 在真实 Intel Mac 上能被**运行**、且行为与 Apple Silicon 一致"——
后者涉及签名/权限对话框、真实 launchd、真实文件系统权限等一整套只有真机
才能验证的东西，Rosetta 转译执行也不等价于原生执行。下面的步骤就是这后
半段。

## 前置条件

- 把 CI 产出的 `daemon-bundle-x64` artifact（round-1 review 修复后是一个
  `tar.gz`——`upload-artifact` 不保权限位/symlink，见
  `.github/workflows/release-bundle.yml` 上传步骤前的注释——下载回来先
  `tar -xzf` 解开）（或本地在 `macos-15-intel` 上跑
  `scripts/release/build-daemon-bundle.sh x64` 的等价产物）接进
  `scripts/release/build-mac.sh` 的打包步骤，产出
  `Jones-<version>-x64.dmg`（这一步本分支未自动化，见上）。
- 一台真实 Intel Mac（非 Rosetta 模拟），macOS 13+。

## 步骤

1. 把 `.dmg` 拷到 Intel 机器，安装、启动。
2. 用 `file`/`lipo -info` 确认 `.app` 内的 daemon 可执行文件与 Python 解释器
   确实是 `x86_64`，不是被 Rosetta 悄悄转译的 arm64 产物。
3. 跑一遍 `docs/acceptance/v1.0/` 里其余已自动化 G 用例对应的手工烟测（至少：
   首轮对话、权限三道闸各一次、Run 回放、Cron、终止一个 Run）。
4. 跑 `make check` 等价的手工验证（Intel 机器上大概率没有开发环境，做
   应用层烟测即可，不要求在 Intel 机器上跑 `pytest`/`vitest`）。
5. 跑一次 `apps/desktop` 的 `pnpm e2e` 等价流程（真实 daemon + 真实 Electron）
   ——如果 Intel 机器上有完整开发环境的话；否则退化为步骤 3 的手工烟测。
