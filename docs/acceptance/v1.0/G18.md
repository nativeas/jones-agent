# G18 — macOS 双架构（Intel 真机）

**状态：待执行，当前被 #36 阻塞**（x86_64 daemon 产物在 arm64 主机上构建失败，
不只是"没有 Intel 真机跑"——根本没有可拿去 Intel 机器上跑的产物）。

> PRD 12.1: "G18 | macOS 先发：G01–G17、G19–G21 在 macOS（Apple Silicon 与
> Intel）上均通过即可发布 v1.0；Windows 版作为 v1.1 单独门禁，复跑同一组 |
> v1.0 跑 macOS 双架构；v1.1 跑 Windows"

## 阻塞项：Issue #36

见 `gh issue view 36 -R nativeas/jones-agent`：`cryptography==50.0.0` 在
PyPI 上没有发布 macOS x86_64 wheel，`uv` 退回源码编译，本机（arm64）没有
`x86_64-apple-darwin` 的 Rust 交叉编译工具链，链接阶段失败。详见
`docs/release.md` §2.2（Q 的实测记录，"比 spike 02 的结论更差，诚实写下"）。
候选方案（#36 原文）：a) CI 用 `macos-13`（Intel）runner 直接出 x86_64 包；
b) 降/换 `cryptography` 到有 x86_64 wheel 的版本并复核 vault AES-GCM 兼容；
c) v1.0 只发 Apple Silicon，Intel 随 v1.1（需要改 PRD G18 与 11.4）。

**本文档不重复 #36 的阻塞分析**，只记录 #36 解除、拿到真实 x86_64 产物之后，
在一台真实 Intel Mac 上要走的验收步骤——这一步骤本身无法在 arm64 开发机 /
GitHub Actions 的 arm64 runner 上模拟（Rosetta 转译执行不等价于原生 x86_64，
尤其涉及 `cryptography` 这类带编译型扩展的依赖时）。

## 前置条件

- #36 已解除，`scripts/release/build-mac.sh x64` 产出可用的
  `Jones-<version>-x64.dmg`。
- 一台真实 Intel Mac（非 Rosetta 模拟），macOS 13+。

## 步骤

1. 把 `.dmg` 拷到 Intel 机器，安装、启动。
2. 用 `file`/`lipo -info` 确认 `.app` 内的 daemon 可执行文件与 Python 解释器
   确实是 `x86_64`，不是被 Rosetta 悄悄转译的 arm64 产物。
3. 跑一遍 `docs/acceptance/v1.0/` 里其余已自动化 G 用例对应的手工烟测（至少：
   首轮对话、权限三道闸各一次、Run 回放、Cron、终止一个 Run）。
4. 跑 `make check` 等价的手工验证（Intel 机器上大概率没有开发环境，做
   应用层烟测即可，不要求在 Intel 机器上跑 `pytest`/`vitest`）。
5. 跑一次 `apps/desktop` 的 `pnpm e2e` 等价流程（真实 daemon + 真实 Electron）
   ——如果 Intel 机器上有完整开发环境的话；否则退化为步骤 3 的手工烟测。

## 期望

- Intel 原生运行，不依赖 Rosetta。
- G01–G17、G19–G21 在这台 Intel 机器上的关键路径（不要求重跑全部自动化用例，
  那些已经在 CI 里对 arm64 跑过；这里验证的是"同一份产物在 Intel 架构上行为
  一致"）表现与 Apple Silicon 上一致。
