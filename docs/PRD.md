# Jones Agent 产品需求文档

## 1. 一句话定义

Jones Agent 是一台装在用户自己电脑上、自主运行的通用 AI 工作体：它以对话 / 聊天 session 为核心，配备文件、终端、浏览器、互联网、媒体生成、办公文档、协作平台等全域能力，能在用户授权的边界内自主完成多步骤工作，并全程可观察、可拦截、可回放。

## 2. 问题定义

市面上的 AI agent 产品存在六种结构性缺陷，Jones Agent 逐一针对：

| # | 现状缺陷 | 用户痛点 | Jones Agent 的回答 |
|---|---|---|---|
| 1 | 摸不到本地环境：网页聊天框 / 云端 agent 看不见用户的磁盘、终端、浏览器登录态 | 「让它整理我的文件夹？它连我的磁盘都看不见」 | 本地常驻 agent；在用户授权前提下可直接操作本地磁盘、终端、浏览器及其登录态 |
| 2 | 账号 + 订阅 + 黑箱：强绑登录、按月收费、模型由厂商锁死 | 「我的数据在谁手里？我想换个模型都不行」 | 用户自行配置 API Key（BYOK），兼容多家大模型厂商，可按需切换 |
| 3 | 能力被产品方裁剪：能接什么工具、读什么服务，由厂商说了算 | 「想让它读我的飞书日程、生成一支视频，做不到」 | 工具协议开放：能接 Skill、能接 MCP 的一切都可以接，用户决定边界 |
| 4 | 动作不可控：要么事事都问，要么全自动黑跑，缺少中间态 | 「它到底对我的文件做了什么？出了问题能追回来吗？」 | 明确的授权边界；每一步动作可拦截、可回放，用户清楚知道每个环节做了什么 |
| 5 | 单会话、无常驻：关掉窗口任务就死，做不了后台、定时、远程派活 | 「我不在电脑前就没法用它」 | 常驻进程；支持多会话并行，同时提供一个总的单会话入口（类 Hermes 的 Telegram 接口）；后续支持从飞书 / 微信 / Telegram 远端派活（P2） |
| 6 | 失败不诚实：报错被吞、假装完成、白屏，用户不敢放手让它跑多步 | 「它说做完了，其实根本没做」 | 失败显式反馈、说明具体情况；同时尽力把任务推进到底而非轻易放弃（类 Hermes agent 的执行风格） |

## 3. 目标用户与核心场景

按优先级分三档：P0 是 v1 主攻人群，P1 顺带覆盖，P2 后续扩展。

| 优先级 | 用户画像 | 核心场景 | 关键能力 |
|---|---|---|---|
| P0 | 自动化爱好者 | 「每天早上 9 点汇总我的收件箱和日程」 | 定时任务 + 常驻进程 + 多会话 |
| P0 | 研究者 / 分析师 | 「调研这个赛道，产出带引用的报告」 | 互联网 + 深度调研 + 文档生成 |
| P1 | 知识工作者 | 「把本周会议纪要整理成待办，写进我的任务清单」 | 飞书 / 办公文档 + 记忆 |
| P1 | 开发者 / 技术用户 | 「重构这个模块，跑通测试，开 PR」 | 文件 + 终端 + 浏览器 + code review |
| P1 | 内容创作者 | 「按这个脚本生成短视频素材并配音」 | 媒体生成套件 |
| P2 | 移动办公者 | 「地铁上用飞书 / TG 给它派活、批准它改文件」 | IM 通道 + 远程授权 |

## 4. 产品形态

- **桌面应用（v1.0 macOS，v1.1 Windows）**：Electron 壳 + 三栏式工作台界面。左栏（会话列表）与右栏（动作流 / 审批面板）均可随时开关，中栏为对话主区。
- **核心运行时**：本地常驻进程，管理会话、任务、调度、存储。
- **会话结构**：一个总的主会话（类 Hermes 的主频道，也是 IM 通道的落点）+ 多个并行子会话；子会话可由主会话派生为独立任务。
- **入站通道**：桌面为主入口；IM（飞书 / 微信 / Telegram）为扩展入口（P2，见 FR21 / FR22）。不做手机伴侣端。
- **无云端依赖**：所有数据落本地（`~/.jones/`）；模型与外部服务由用户自行配置。

## 5. 产品原则（不可妥协项）

以下八条是产品宪法。任何功能设计与之冲突，改功能不改原则。

1. **本地优先**：用户数据（对话、记忆、任务、凭据）默认只存本机 `~/.jones/`；不提供云端同步。
2. **无账号、BYOK**：没有注册、登录、SSO、订阅。进门唯一门槛是用户自己的模型 Key；兼容多家大模型厂商。
3. **能力透明**：本轮给 agent 装配了哪些工具、隐藏了哪些、为什么，用户在设置页随时可查。能力清单由装配层注册表生成，永不手写。
4. **动作可拦**：任何改变外部世界的动作（写文件、发消息、联网外发）默认经过用户批准；拒绝即不执行，执行即留痕、可回放。
5. **失败诚实**：错误显式呈现（网络、配额、工具异常），永不白屏、永不静默吞错、永不让 agent 假装成功；在诚实的前提下尽力推进任务。
6. **开放扩展**：Skill、MCP 及任何可接协议均开放给用户；产品方不裁剪能力边界，用户决定边界。
7. **不可逆操作零容忍**：不可逆的删除类操作永不自动执行；任何授权、任何模式都无法覆盖这条。
8. **重启不自动重放**：进程重启后，排队中的外发消息 / 待执行动作不自动发送或执行，需用户重新确认。

## 6. 总体技术架构

### 6.1 分层

```
┌──────────────────────────────────────────────────────┐
│ ① 桌面壳  Electron（Renderer: React 三栏 UI）             │  只做展示与交互，无 Node 权限
├──────────────────────────────────────────────────────┤
│ ② Agent 运行时  独立守护进程（Python）                    │  Electron 关闭后仍常驻
│    - Session Manager   主会话 + 子会话                    │
│    - Task Scheduler    Cron、后台任务                     │
│    - Channel Gateway   桌面 / 飞书 / 微信 / Telegram       │
│    - Permission Gate   三道闸：规则 / 审查 / 用户           │
│    - Store             SQLite + 文件系统 + 多模态向量库     │
├──────────────────────────────────────────────────────┤
│ ③ Agent 内核 + 模型层  复用 Hermes 循环引擎（Python）       │  与运行时同语言，按会话拉起 worker
│    - 循环引擎 / 上下文管理 / 记忆                          │
│    - 多厂商模型适配                                      │
├──────────────────────────────────────────────────────┤
│ ④ 能力域  Tools / Skills / MCP                          │  文件、终端、浏览器、互联网、媒体、办公、协作
└──────────────────────────────────────────────────────┘
```

### 6.2 分层铁律

- UI 进程（Renderer）无 Node 权限；一切能力经 IPC 走运行时。
- 循环引擎不自研，直接复用 Hermes agent 的成熟内核。
- 能力域不反向依赖 UI，也不反向依赖运行时的会话 / 通道模块。
- 运行时是独立守护进程：Electron 是它的一个前端，IM 通道是另一个前端；两者地位对等。
- 运行时与内核同为 Python，Hermes 以库形式引入，不跨语言桥接。

### 6.3 进程与桥接

| 边界 | 方式 |
|---|---|
| Electron Renderer ↔ Electron Main | Electron IPC（contextBridge 白名单） |
| Electron Main ↔ 运行时守护进程 | 本地 socket（Unix socket / Named pipe），JSON-RPC |
| 运行时 ↔ 内核 worker | 同为 Python；运行时按会话拉起独立 worker 子进程，stdio 通信，保证会话间隔离、单个 worker 崩溃不拖垮守护进程 |
| 运行时 ↔ IM 平台 | 各平台官方 SDK / Bot API（长连接或 Webhook） |
| 内核 ↔ 能力域 | Hermes 原生 tool 协议 + MCP client；Skill 以文件形式加载 |

### 6.4 存储

全部落在 `~/.jones/`（详细目录布局与存储规则见第 10 节）：

- **SQLite**：会话、消息、任务、审批记录、工具调用日志（回放的事实源）。
- **文件系统**：附件、生成的媒体、Skill 定义、MCP 配置、凭据（加密）。
- **多模态向量库**：长期记忆与检索，文本 / 图像 / 音频统一向量化，供内核记忆层调用。

### 6.5 多模型适配

统一走 Hermes 的模型适配层；用户在设置页按厂商配置 Key，可为不同会话 / 任务指定不同模型。

v1 首批支持：Anthropic、OpenAI、DeepSeek、Qwen、Gemini、本地 Ollama。新增厂商以 adapter 形式接入，不改动内核。

## 7. 核心对象模型

### 7.1 核心对象（v1 必需）

| 对象 | 定义 | 关键关系 |
|---|---|---|
| **Project** | 工作区。以一个目录路径为锚点，把该目录下的多个 Session 归组管理、统一操作 | 1 Project : N Session |
| **Agent** | 智能体。一个人格 + 一套能力天花板的组合：人设、语气、原则、工具白名单、Skill 集合、模型偏好 | Session 绑定 1 Agent；Agent 可被多个 Session 复用 |
| **Session** | 一次对话。分主会话（唯一、常驻、IM 落点）和子会话 | 归属 1 Project、绑定 1 Agent；1 主 : N 子 |
| **Message** | 用户 / agent / 系统 / 工具消息，按时间线归属 Session | N : 1 Session；归属 1 Turn |
| **Turn** | 轮次。一个用户输入触发的一次完整运行，直到 agent 交还控制权 | N : 1 Session；1 Turn 产生 1 Run |
| **Task** | 可独立追踪的工作单元。来源：用户派活、Goal 拆解、Cron 触发、子会话派生 | 关联 1 Session；有状态机 |
| **Run** | 一次执行：agent 循环从起点到结束。**回放的最小单位** | N : 1 Task；由 Turn 或 Cron 触发；含完整 Step 序列 |
| **Step** | Run 内一次工具调用：参数、结果、耗时、审批结果 | N : 1 Run；关联 1 Permission Decision |
| **Permission Decision** | 一次动作的权限裁决：过了哪道闸、谁批的、结果 | 1 : 1 Step |
| **Skill** | agent 可加载的技能包（文件形式），扩展其能力 | Agent 引用 N Skill |
| **Goal** | 长效目标。跨多个 Turn / Run 持续推进，可拆解为多个 Task | 归属 1 Session 或 1 Project；1 Goal : N Task |
| **Cron** | 定时任务：Cron 表达式 + 目标 prompt / Task 模板 | 触发生成 Task → Run |

### 7.2 支撑对象

| 对象 | 定义 | 优先级 |
|---|---|---|
| **Channel** | 入站通道（飞书 / 微信 / Telegram）及其绑定的外部身份，落到主会话 | P2（随 FR21） |
| **Capability** | 已装配的能力项（内置 Tool / Skill / MCP Server），由注册表维护 | P0（Agent 白名单依赖它） |
| **Memory** | 长期记忆条目（文本 / 多模态），带来源与向量，跨 Session 检索 | P1 |
| **Model Config** | 厂商 Key、模型、默认路由；Agent 偏好可覆盖 | P0 |
| **Credential** | 外部服务凭据（加密存储），Capability 引用 | P0 |

### 7.3 对象关系图

```
Project ─┬─ Session (主) ──┬─ Turn ─── Run ─── Step ─── Permission Decision
         │      │          └─ Message
         │      ├─ Agent (人设 / 原则 / 工具白名单 / Skill / 模型偏好)
         │      └─ Session (子) ...
         ├─ Goal ─── Task ─── Run          (Goal 亦可挂在单个 Session 下)
         └─ Cron ─── Task ─── Run
```

## 9. 行为契约

### 9.1 工作模式

Session 级别可切换三种工作模式，决定 agent 在本会话内「能不能碰工具、碰了谁来批」：

| 模式 | 定位 | 工具调用 | 权限闸 | 典型场景 |
|---|---|---|---|---|
| **纯对话模式** | 只聊，不动手 | 禁止调用任何工具（含只读工具） | 不涉及 | 头脑风暴、问答、写作润色 |
| **任务模式** | 默认模式，动手但事事留痕 | 允许；只读工具直接放行，改变外部世界的动作逐条走三道闸 | 规则闸 → 审查闸 → 用户闸，全开 | 日常派活：整理文件、跑脚本、调研出报告 |
| **自动模式** | 少打断，放手跑 | 允许；在 Agent 工具白名单与规则闸允许范围内直接执行，不逐条弹用户闸 | 规则闸、审查闸仍生效；用户闸仅对审查闸判定的高危动作弹出 | Cron 定时任务、长链路调研、用户明确说「你自己跑完」 |

模式边界（不随模式变化）：

- 第 5 节第 7 条在任何模式下生效：**不可逆删除永不执行**，自动模式也不例外。
- 自动模式不是「绕过权限」：它只是把用户闸的触发条件从「每个写动作」收窄为「审查闸标红的动作」。规则闸里用户明确禁止的动作，三种模式下都不会执行。
- 模式切换即时生效，作用于该 Session 后续的 Turn；正在执行中的 Run 不受影响。
- Cron 触发的 Run 默认以自动模式运行；用户可在 Cron 定义里改为任务模式（此时待审动作挂起，等用户回来批）。

### 9.2 排队与并发

- **同一 Session 内串行**：当前 Turn 运行中收到新指令，新指令进入该 Session 的队列，不打断当前 Turn；当前 Turn 结束后按入队顺序依次执行。队列中的指令用户可查看、可撤回、可调序。
- **多 Session 并行**：不同 Session 各自独立运行，互不阻塞、互不共享队列；并发上限由用户在设置中配置。
- **重启后队列恢复但不自动发送**：守护进程重启后，各 Session 未执行的队列指令恢复为「待发送」状态，UI 显式提醒「有 N 条未发送的输入」；必须由用户显式触发（点击发送 / 回车）才进入执行。呼应第 5 节第 8 条。

### 9.3 终止

三类终止，处理方式不同，但共同要求：**终止后的状态必须显式可见，永不出现「看起来在跑、其实已死」**。

| 终止类型 | 触发条件 | 处理方式 | 上下文保留 |
|---|---|---|---|
| **用户终止** | 用户手动点击停止 / 取消 | 停止模型对话；正在执行的工具调用完整收尾（不留半截状态），不再发起新调用 | 已完成的 Step 结果保留进 Session 上下文，后续 Turn 可引用 |
| **错误终止** | 网络、工具异常、内核崩溃、模型返回不可恢复错误 | 整个 Turn 终止；在对话流中插入显式**错误卡片**：错误类型、发生在哪个 Step、原始错误信息、可选操作（重试 / 换模型 / 放弃） | 错误发生前的 Step 结果保留；错误卡片本身进入 Session 记录，可回放 |
| **预算终止** | 触发 Goal 的 token 预算上限；远端 API Key 额度受限 / 被限流；或触顶 11.2 的单 Run Step 数 / 时长上限 | 收到该类信号后立即停止发起新调用，当前工具调用完整收尾；显式卡片说明是哪个预算、用了多少、上限多少 | 全部保留；用户提高预算 / 换 Key 后**重新发起**新 Turn，已完成的 Step 结果在上下文中可用；断点续跑不在 v1 范围 |

终止的通用规则：

- 三类终止都记录进 Run，回放时可见终止点与终止原因。
- 终止不清空 Session 队列；队列中的后续指令挂起，等用户决定继续或清空。
- 自动模式下的 Cron Run 发生错误或预算终止时，结果推回主会话并附带错误卡片，不静默失败。

### 9.4 审批超时

用户闸弹出后无人处理时的行为：

- **默认不超时、不自动放行**：待审动作一直挂起，Run 处于「等待审批」状态并在 UI 明确标示；不因等待时间长而自动批准或自动拒绝。
- **超时可配置，但只能配「拒绝」**：用户可在设置中为待审动作设置超时（如 30 分钟），超时后自动**拒绝**并终止当前 Run（按 9.3 错误终止处理，卡片注明「审批超时」）。不提供「超时自动批准」选项——这等于绕过用户闸。
- **待审期间其它 Session 不受影响**：只阻塞当前 Session 的当前 Run；同 Session 队列中的后续指令继续挂起。
- **Cron Run 的待审动作**：推回主会话提醒；用户不在时挂起到下一次打开桌面端或 IM 端处理（IM 远程审批为 P2）。

### 9.5 上下文与记忆写入规则

区分两层：**会话上下文**（Session 内、随对话自然积累）与**长期记忆**（跨 Session、落向量库）。

| | 会话上下文 | 长期记忆 |
|---|---|---|
| 写入时机 | 每个 Turn 自动写入 Message / Step 结果 | 仅在下列情形写入：① 用户显式说「记住 …」；② agent 在 Run 结束时提议「以下内容是否存入记忆」，**用户确认后写入**；③ Agent 配置中开启「自动记忆」的 Agent，可自动写入，但每条记忆带来源标记且用户可见 |
| 写入内容 | 全量 | 只写结论、偏好、事实性信息；不写原始文件内容、凭据、Key、大段工具输出 |
| 可见性 | Session 内可见 | 设置页「记忆」面板全量可查、可编辑、可删除、可导出 |
| 检索 | 由内核按上下文窗口策略管理 | 每个 Turn 开始时按相关性检索注入；注入了哪几条在 Run 回放中可见 |
| 隔离 | 按 Session | 默认按 Project 隔离；用户可将某条记忆标为「全局」跨 Project 生效 |

红线：凭据、完整 API Key、用户明确标记为敏感的内容，任何路径都不进长期记忆。

### 9.6 子会话派生规则

- **派生来源**：① 用户在主会话中显式说「另开一个会话去做 X」；② agent 在任务模式 / 自动模式下判断某子任务适合独立跑，**提议派生，用户确认后创建**；③ Goal 拆解出的 Task 默认各自派生子会话；④ Cron 触发的 Run 默认在独立子会话中运行。
- **继承**：子会话继承父会话的 Project、Agent、工作模式；继承父会话的**摘要上下文**（由派生时的 prompt 携带），不继承完整消息历史。
- **权限不放大**：子会话的工具白名单 ⊆ 父会话；父会话是任务模式，子会话不能是自动模式（反向可以收紧）。
- **回传**：子会话结束（正常 / 终止）后，将结果摘要作为一条系统消息回传父会话；父会话可展开查看子会话完整记录与回放。
- **生命周期**：子会话独立运行，不因父会话终止而终止；用户可在左栏树状结构中看到父子关系，可单独终止 / 删除子会话。
- **深度限制**：子会话默认最多再派生一层（即最深三层：主 → 子 → 孙），防止无限分叉；可在设置中调整。

## 10. 数据与存储

全部数据落在本机，无云端副本。分两个根：**`~/.jones/`** 是用户级根目录（基础启动环境，所有 Project 共用）；**`<项目目录>/.jones/`** 是项目级根目录（该 Project 的定制化设定，随项目目录走）。三种存储介质各司其职：**SQLite** 存结构化记录与事实源，**文件系统**存大块内容与配置，**向量库**存可检索的记忆。

### 10.1 八类数据一览

| # | 数据类别 | 用户级 `~/.jones/` | 项目级 `<项目目录>/.jones/` |
|---|---|---|---|
| 1 | 会话历史 | `jones.db`（Session / Turn / Message / Run / Step）+ `runs/` payload | — （会话按 project-id 关联，不落项目目录，避免污染用户仓库） |
| 2 | 运行时状态 | `runtime/`：守护进程 PID、worker 注册表、Session 队列快照、Cron 下次触发时间、进行中 Run 的检查点 | — |
| 3 | 凭据 | `secrets/vault.enc` | — （凭据永不落项目目录） |
| 4 | 记忆 | `memory/global/` 全局记忆 | `.jones/memory/` 该项目的向量库分片 |
| 5 | 人格（Agent） | `agents/` 用户级 Agent 库 | `.jones/agents/` 项目专属 Agent 或对用户级 Agent 的覆盖 |

| 8 | 工作区 / 启动环境 | `config/settings.json`、`providers.json`、`permissions.json`：全局默认 | `.jones/settings.json`、`.jones/permissions.json`：项目级覆盖（如默认 Agent、默认模式、该项目的额外允许 / 禁止规则） |

合并规则：项目级设定**覆盖**用户级同名项；权限规则例外——项目级只能**收紧**不能放宽（项目里写「允许 rm」无效，写「禁止 git push」有效）。

### 10.3 存什么、存哪里

| 数据 | 介质 | 位置 | 保留策略 | 用户可操作 |
|---|---|---|---|---|
| Project、Agent、Session、Turn、Message | SQLite | `jones.db` | 永久，用户删除即删 | 查看 / 导出 / 删除 |
| Task、Run、Step（元数据：参数、状态、耗时、结果摘要） | SQLite | `jones.db` | 永久；**回放的事实源** | 回放 / 导出 / 删除 |
| Step 的大块 payload（工具完整输出、截图、终端全文） | 文件系统 | `runs/<run-id>/` | 默认保留 90 天，可配置；删 Run 时联动删除 | 回放时按需加载 |
| Permission Decision（审批记录） | SQLite | `jones.db` | 永久，**不可被 agent 删除**，只能用户删 | 查看 / 导出 |
| Goal、Cron 定义与触发历史 | SQLite | `jones.db` | 永久 | 编辑 / 停用 / 删除 |
| Session 队列（未执行指令） | SQLite | `jones.db` | 重启后恢复为「待发送」 | 查看 / 撤回 / 调序 |
| 运行时状态（PID、worker 注册表、Cron 下次触发、进行中 Run 检查点） | 文件 | `runtime/` | 守护进程启动时校验并重建；崩溃后据此恢复 Run 为「中断」状态 | 只读查看 |
| 长期记忆（文本 / 多模态向量 + 原文 + 来源） | 向量库 | `<项目目录>/.jones/memory/`、`~/.jones/memory/global/` | 永久，用户可删 | 查看 / 编辑 / 删除 / 导出 |
| API Key、外部凭据、IM Bot Token | 加密文件 | `secrets/vault.enc` | 永久 | 设置页增删；**UI 永不完整回显** |
| 全局设置、规则闸、厂商路由、MCP 配置 | JSON | `~/.jones/config/`；项目级覆盖在 `<项目目录>/.jones/` | 永久 | 设置页编辑；也可手改文件 |
| Agent 定义 | 文件 | `~/.jones/agents/`、`<项目目录>/.jones/agents/` | 永久 | 设置页编辑 / 导入导出 |
| Skill | 文件 | `~/.jones/skills/`、`<项目目录>/.jones/skills/` | 永久 | 安装 / 卸载 |
| 附件、生成媒体 | 文件系统 | `projects/<id>/attachments/` | 永久，随 Project 删除 | 打开 / 导出 / 删除 |
| 守护进程 / worker 日志 | 文件 | `logs/` | 滚动保留 7 天 | 打开日志目录 |
| 网页抓取缓存、模型响应缓存 | 文件 | `cache/` | 可随时清空 | 一键清空 |

### 10.4 存储规则

- **事实源唯一**：回放、审批追溯、任务状态一律以 SQLite 为准；文件系统里的 payload 是它的附属，丢了只影响回放细节，不影响状态正确性。
- **agent 不能碰自己的记录**：`jones.db`、`secrets/`、`config/permissions.json` 对 agent 的文件工具不可见、不可写；agent 只能通过运行时暴露的受控接口读自己的会话上下文。
- **项目级 `.jones/` 对 agent 半开放**：`agents/`、`skills/`、`mcp.json`、`settings.json` 可读（agent 需要知道自己的配置）；`permissions.json` 与 `memory/` 不可写，写入只能走运行时接口。
- **凭据只进 vault**：任何路径（记忆、日志、回放 payload、错误卡片）出现完整 Key / Token 时在写入前脱敏。
- **删除是真删**：用户删 Session / Project / 记忆时，SQLite 行、关联 payload、向量分片一起删；提供「导出后删除」选项。
- **可整体迁移**：`~/.jones/` 整个目录拷到另一台机器即完成迁移；`secrets/vault.enc` 因绑定系统密钥链需重新录入 Key。
- **不可逆删除永不由 agent 执行**：包括对 `~/.jones/` 自身的删除，呼应第 5 节第 7 条。

## 11. 非功能需求

### 11.1 启动性能

以「用户双击图标 → 能开始打字」为口径，在中端机（Apple M1 / 16GB；Intel i5 12 代 / 16GB）上：

| 阶段 | 指标 | 说明 |
|---|---|---|
| 桌面壳可见 | ≤ 1.5 s | Electron 窗口出现三栏骨架，不要求内容就绪 |
| 可开始输入 | ≤ 3 s | 会话列表加载完成、输入框可用；守护进程已在运行的情况下 |
| 冷启动（守护进程未运行） | ≤ 6 s | 含拉起 Python 守护进程、加载 SQLite、恢复队列快照 |
| 首个 Turn 首 token | ≤ 模型 RTT + 800 ms | 800 ms 是运行时 + worker 拉起 + 记忆检索的总开销上限 |
| 冷启动 worker | ≤ 2 s | 新 Session 首次拉起 Python worker 子进程；后续复用 |

- 守护进程随系统登录自启（可关），多数情况下用户遇到的是热启动。
- 启动阶段任何一步超过阈值 2 倍仍未完成，UI 显式提示「正在恢复 … 」并给出跳过 / 重启选项，不白屏。

### 11.2 运行时限制

| 项 | 上限 | 说明 |
|---|---|---|
| 守护进程常驻内存（空闲） | ≤ 150 MB | 无活跃 Session 时 |
| 单个 worker 子进程 | ≤ 500 MB | 超出则该 worker 按 9.3 错误终止并回收，不影响其它 Session |
| Electron 壳（Main + Renderer） | ≤ 300 MB | 三栏 UI、单窗口 |
| 全部合计（空闲） | ≤ 500 MB | 用户可在设置页看到实时占用 |
| 并发 Session 默认上限 | 4 | 可配置 1–16；超出的排队 |
| 单个 Run 最大 Step 数 | 200 | 防死循环；可在 Agent 配置中放宽，触顶按预算终止处理 |
| 单个 Run 最大时长 | 2 h | 同上 |
| 单 Session 上下文 | 由模型窗口决定 | 内核负责压缩；压缩事件在回放中可见 |
| 空闲 CPU | ≈ 0 | 无任务时不轮询；Cron 用系统定时器唤醒 |

### 11.3 系统设计：稳定性、安全性、隐私

**稳定性**

- **进程隔离**：守护进程、每个 worker、Electron 三者独立；任一 worker 崩溃只影响它的 Session。
- **守护进程托管**：守护进程注册为系统用户级服务（macOS launchd / Windows 任务计划），崩溃后由系统拉起，Electron 未运行时也成立（G11 依赖此点）；Electron 运行时额外检测守护进程健康，连续 3 次拉起失败则显式报错。
- **崩溃恢复**：守护进程启动时校验 `runtime/` 检查点，把进行中的 Run 标为「中断」并推送卡片，不假装继续。
- **写入原子性**：SQLite 开 WAL；配置文件写入先写临时文件再 rename。
- **外部依赖降级**：模型 API 不可达 → 错误卡片 + 可切换厂商；向量库不可用 → 记忆检索跳过并在回放中标记，Turn 照常进行。
- **升级不丢数据**：SQLite schema 带版本号，升级时自动迁移；迁移前自动备份 `jones.db`。

**安全性**

- **最小权限**：Renderer 无 Node 权限；agent 的文件工具默认限定在 Project 工作区，越界访问走权限闸。
- **凭据**：只存 `secrets/vault.enc`，密钥由系统密钥链派生；进程内存中的 Key 用后即清；UI、日志、回放、记忆全路径脱敏。
- **三道闸不可绕过**：权限判定在守护进程内完成，worker 与 agent 无法自行放行；不可逆删除硬编码拒绝。
- **供应链**：Skill 与 MCP Server 安装时展示其声明的能力与权限需求；第三方 Skill 默认不进白名单，需用户显式启用。
- **本地端口**：守护进程只监听 Unix socket / Named pipe，不开 TCP 端口；IM 通道用出站长连接，不需要入站端口。

**隐私**

- **零遥测**：不上报任何使用数据、崩溃日志；如需诊断，用户手动导出日志包。
- **数据不出本机**：除用户配置的模型 API 与显式启用的外部服务外，程序不发起任何网络请求。
- **发给模型的内容可见**：每个 Turn 实际发送给模型的 prompt（含注入的记忆、工具结果）在回放中完整可查。
- **敏感目录默认屏蔽**：`~/.ssh`、`~/.aws`、浏览器 profile、系统密钥链等对 agent 文件工具默认不可见；用户可在规则闸中显式放开。

### 11.4 技术指标：可扩展性与兼容性

**可扩展性**

| 扩展点 | 机制 | 用户是否需要改代码 |
|---|---|---|
| 新模型厂商 | Hermes 模型适配层 adapter | 否（配置）/ 是（新协议） |
| 新工具 | MCP Server | 否 |
| 新技能 | Skill 文件包 | 否 |
| 新 Agent 人格 | `agents/` 目录定义 | 否 |
| 新 IM 通道 | Channel Gateway 插件接口 | 是（P2） |
| 新存储后端（向量库） | Store 层接口 | 是 |

- 能力注册表是唯一装配入口：任何来源的工具进入注册表后，白名单、权限闸、透明页自动覆盖，不需要逐个适配。
- 数据规模目标：单库支撑 ≥ 10 万条 Message、≥ 1 万个 Run、≥ 10 万条记忆向量而不劣化交互延迟；超出时按 10.3 保留策略归档。

**兼容性**

| 维度 | 范围 |
|---|---|
| 操作系统 | v1.0：macOS 13+（Apple Silicon 与 Intel）；v1.1：Windows 10 21H2+ / Windows 11（x64） |
| Python 运行时 | 随程序打包，不依赖用户系统 Python |
| 浏览器能力 | 复用用户已安装的 Chrome / Edge（Chromium 内核）；Safari 不支持 |
| 模型协议 | Anthropic Messages、OpenAI Chat Completions 及其兼容实现（DeepSeek / Qwen / Ollama）、Gemini |
| MCP | 遵循 MCP 官方规范，stdio 与 HTTP（SSE / Streamable）两种传输 |
| Skill 格式 | 与 Hermes 原生 Skill 格式兼容；现有 Hermes Skill 可直接加载 |
| 数据迁移 | `~/.jones/` 整目录跨机器可用（凭据需重录）；跨版本自动迁移 |
| 离线 | 除模型调用外全部功能离线可用；搭配 Ollama 可完全离线 |

## 12. 验收标准

验收分三层：**12.1 发布门禁**是 v1 发布的强制通过条件，缺一不发；**12.2 负面清单**是任何版本、任何环境下绝对不能发生的事，出现即阻断发布并回滚；**12.3 Feature 验收**是 P0 各项的逐条验收口径。QA 用例、发布检查单均以本节为准。

### 12.1 发布门禁（v1 强制通过，缺一不发）

| # | 条件 | 验证方式 |
|---|---|---|
| G01 | 全程无账号：从安装到完成首个 Turn，不出现注册 / 登录 / 订阅任何入口 | 全新机器走一遍安装到首轮对话 |
| G02 | BYOK 生效：六家厂商（Anthropic、OpenAI、DeepSeek、Qwen、Gemini、Ollama）配 Key 后均可正常完成 Turn | 每家跑一个含工具调用的 Turn |
| G03 | Key 永不完整回显：设置页、日志、回放、错误卡片、记忆中均不出现完整 Key | 全文 grep 已配置的 Key 字符串，命中数为 0 |
| G04 | 三道闸生效：规则闸禁止项被拦、审查闸对高危动作标红、用户闸拒绝即不执行 | 三条用例各一，分别验证拦截、标红、拒绝后无副作用 |
| G05 | 不可逆删除永不执行：自动模式下 agent 尝试 `rm -rf` / 清空回收站 / 永久删除文件，均被硬拒 | 三种模式各跑一遍 |
| G06 | 三种工作模式行为符合 9.1：纯对话模式零工具调用；任务模式写动作逐条弹闸；自动模式规则闸内不弹 | 同一任务三种模式各跑一遍，比对回放 |
| G07 | Run 回放完整：任一 Run 可回放全部 Step 的参数、结果、耗时、审批结果、发送给模型的完整 prompt | 随机抽 5 个 Run 回放，与实时记录比对 |
| G08 | 异常显式报错不崩溃：断网、Key 失效、工具抛异常、worker 被 kill 四种故障下，UI 出错误卡片，进程不崩、不白屏、不静默 | 四种故障注入 |
| G09 | 用户终止收尾干净：Run 中途停止后，正在执行的工具调用完整结束，无半截文件、无孤儿进程 | 在文件写入与终端命令中途停止 |
| G10 | 重启不自动重放：队列中有 3 条未发送指令时 kill 守护进程再启动，3 条均为「待发送」且 UI 有提醒 | 按描述操作 |
| G11 | 守护进程独立常驻：关闭 Electron 后 Cron 仍按时触发；重开 Electron 能看到结果 | 设 1 分钟 Cron，关窗等待，重开验证 |
| G12 | 多 Session 隔离：4 个 Session 并行，其中 1 个 worker 被 kill，其余 3 个不受影响 | 并行跑 4 个长任务，kill 其一 |
| G13 | Project 隔离：Project A 的记忆、Agent、Skill 在 Project B 中不可见（除标为全局者） | 双 Project 交叉验证 |
| G14 | 权限只能收紧：项目级 `permissions.json` 写「允许」用户级禁止项，实际仍被拦 | 按描述配置并触发 |
| G15 | 敏感目录默认不可见：agent 尝试读 `~/.ssh`、`~/.aws`、`~/.jones/secrets/`，均被拒且走权限闸提示 | 三个路径各一次 |
| G16 | 零遥测：全程抓包，除用户配置的模型 API 与显式启用的外部服务外无任何出站请求 | 安装 → 使用 1 小时 → 关闭，全程抓包 |
| G17 | 启动与内存达标：11.1 / 11.2 的全部指标在参考机上通过 | 自动化性能用例 |
| G18 | macOS 先发：G01–G17、G19–G21 在 macOS（Apple Silicon 与 Intel）上均通过即可发布 v1.0；Windows 版作为 v1.1 单独门禁，复跑同一组 | v1.0 跑 macOS 双架构；v1.1 跑 Windows |
| G19 | 数据可迁移：`~/.jones/` 整目录拷到另一台机，重录 Key 后会话历史、Agent、Skill、记忆完整可用 | 跨机迁移 |
| G20 | 真删：删除 Session / Project / 记忆后，SQLite 行、payload 文件、向量分片均不存在 | 删除后检查磁盘 |
| G21 | 能力透明一致：透明页列出的工具集合与该 Turn 实际装配给模型的工具集合完全一致，含 MCP 与 Skill 来源的工具 | 接入 1 个 MCP、1 个 Skill 后比对透明页与回放中的 tool 列表 |

| # | 绝对不能发生 | 对应原则 |

| N03 | 用户拒绝的动作仍被执行，或用户闸弹出前动作已发生 | 5.4 |
| N04 | 重启后自动发送了排队中的消息或执行了排队中的动作 | 5.8 |
| N05 | 用户数据（对话、记忆、凭据、文件内容）被发送到用户未配置、未显式启用的任何远端 | 5.1、11.3 |
| N06 | 出现遥测、崩溃上报、使用统计等任何形式的自动上报 | 11.3 |

| N16 | 白屏、无响应窗口、需要强制退出才能恢复的挂死 | 5.5 |
| N17 | 升级后会话历史、记忆、Agent 定义丢失或不可读 | 11.3 |

## 13. 实施周期与里程碑

v1.0（macOS）实施周期 **6 周**，按「先把骨架跑通、再逐层加能力、最后收口验收」排；每周末有可演示的产出。Windows（v1.1）在 v1.0 发布后另起 2 周。

| 周 | 里程碑 | 交付物 | 覆盖 Feature | 周末可演示 |
|---|---|---|---|---|
| W1 | 骨架跑通 | Python 守护进程 + Unix socket JSON-RPC；Electron 三栏壳（React）；SQLite schema v1；Hermes 内核以库引入并能跑一个纯对话 Turn | FR01（壳）、FR04（单厂商）、FR15（常驻） | 打开 App → 和模型对话 → 关掉 App 守护进程还活着 |
| W2 | 对象模型与会话 | Project / Agent / Session / Turn / Run / Step 落库；主会话 + 子会话；Session 队列与串行执行；worker 子进程按会话拉起、stdio 通信 | FR01、FR02、FR03、9.2 | 多个 Session 并行跑，队列排队，kill 一个 worker 其余不受影响 |
| W3 | 权限与回放 | 三道闸（规则 / 审查 / 用户）；审批面板；不可逆删除硬拒；Run 回放（Step 级前进后退）；三种工作模式 | FR05、FR06、9.1、9.3、9.4 | 同一任务三种模式各跑一遍，回放对比；试 `rm -rf` 被拒 |
| W4 | 能力域 | 文件五件套、终端、浏览器、互联网 + 深度调研；能力注册表；MCP 接入（stdio + HTTP）；Skill 加载机制 | FR07–FR10、FR13、FR12（加载）、FR16 | 给一个课题，agent 调研出带引用报告；接一个外部 MCP Server |
| W5 | 自动化与存储收口 | Cron 定时任务；BYOK 六厂商；内置 Skill（办公文档、媒体生成）；`~/.jones/` 与项目级 `.jones/` 全部落位；凭据 vault；错误卡片 | FR11、FR12（内置）、FR14、第 10 节 | 设一个 Cron，关窗等触发；六家厂商切换；断网出卡片 |

### 13.1 排期规则

- **P1 不占 6 周**：FR17–FR20 在 W4–W5 若有余量可顺手带，但不进里程碑、不阻塞发布。
- **每周门禁**：当周里程碑「周末可演示」项做不出来，下周不开新 Feature，先补。
- **W3 是不可压缩的**：权限与回放是产品宪法的落地点，宁可砍 W4 的能力域范围（比如浏览器降到 P1），不动 W3。
- **负面清单从 W3 起每日跑**：N01–N18 中可自动化的项（N01–N04、N07、N12、N14）进 CI，每次提交跑。

### 13.2 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Hermes 内核接口不满足「Step 级拦截」需求 | W3 权限闸无法在工具调用前介入 | W1 即验证 Hermes 的 tool-call hook 点；不够则在运行时层包一层代理，工具调用先过守护进程 |
| 多模态向量库选型 | W5 记忆落地延期 | 记忆是 P1（FR18），v1 只落 Store 层接口与目录结构，向量库可用文本版先顶 |
| Electron + Python 打包签名公证 | W6 发布卡壳 | W1 就把「空壳 + 空守护进程」的签名公证流程走通一次 |
| 浏览器复用登录态在不同 Chromium 版本上不稳定 | FR09 验收不过 | 明确只支持 Chrome / Edge 稳定版最近两个大版本；不过则 FR09 降 P1 |

## 14. 明确不做

以下内容在 v1 及可见的后续版本中明确不做；与产品原则（第 5 节）直接对应。

- **登录 / 注册 / SSO / 订阅体系**：违反「无账号、BYOK」。
- **云端同步、云端存储、云端运行时**：违反「本地优先」。
- **移动端 App / 手机伴侣端**：入口只有桌面与 IM 通道。
- **自研基础模型**：只做多厂商适配，不训练、不微调模型。
- **绕过权限闸的「全自动」模式**：任何模式都不能跳过三道闸，不可逆删除永不执行。
- **自研 agent 循环引擎**：直接复用 Hermes 内核（Python），不重造，也不做跨语言移植。
- **产品方裁剪能力边界**：不做「白名单之外一律禁止」的封闭插件市场；能接 Skill / MCP 的都可以接，边界由用户决定。
- **静默重试与静默降级**：失败必须显式呈现，重试 / 换模型的决定权在用户。
